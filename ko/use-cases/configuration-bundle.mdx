# ConfigurationBundle 검증·Diff·적용하기

**완성 결과:** Object와 Internet Access 정책을 하나의 YAML로 정의하여 사전 검사와 변경점 검토 후 Server에 적용합니다.

## 1단계 — 서버 상태와 원본 저장

**Server 셸:**

~~~bash
sudo drlink system version
sudo drlink show status
sudo drlink system revisions
sudo drlink system export configuration /tmp/drlink-before.yaml
~~~

현재 Revision과 버전을 기록합니다. Export 파일에는 민감한 운영 정보가 포함될 수 있으므로 공개 저장소에 업로드하지 않습니다.

## 2단계 — 서버에 적용할 YAML 준비

**Server 셸**에서 **/tmp/drlink-allow-github.yaml**을 생성하고 다음 내용을 넣습니다. 문서용 203.0.113.10은 프록시가 실제 관찰하는 출발지 IP로 바꿉니다.

~~~yaml
configurationBundle:
  context: server
  networkObjects:
    - name: office-admin
      type: ip
      value: 203.0.113.10
    - name: github
      type: fqdn
      value: github.com
  serviceObjects:
    - name: https
      type: tcp
      port: 443
  internetAccess:
    mode: whitelist
    enforcement: enabled
    rules:
      - name: github-https
        source: office-admin
        destination: github
        service: https
        enabled: true
~~~

서버용 스키마는 **configurationBundle / context: server**입니다. apiVersion, kind, Agent용 remoteServices를 추가하지 마세요. 생략한 기존 Rule은 유지되므로 전체 허용 범위를 확인해야 합니다.

## 3단계 — 적용 전 검사

**Server 셸:**

~~~bash
sudo drlink test configuration /tmp/drlink-allow-github.yaml
sudo drlink system diff configuration /tmp/drlink-allow-github.yaml
sudo drlink show internet-access
~~~

**성공 기준:** 문법과 Selector 검사 통과, 예상한 Object/Rule만 Diff에 표시됩니다. Revision이 변경되어 STALE_CONFIGURATION_REVISION이 뜨면 최신 상태를 다시 Export해서 충돌을 해결합니다.

## 4단계 — 승인 후 실제 적용

보안 영향과 확인 안내를 검토한 다음:

~~~bash
sudo drlink system apply configuration /tmp/drlink-allow-github.yaml
sudo drlink show internet-access
sudo drlink system revisions
~~~

**확인:** 새 정책이 신규 연결에 반영되며 동일 변경 재적용 시 상태와 Revision이 일치하면 **NO CHANGE**가 예상됩니다. 서버 번들은 서버 내부에서만 원자적이며 Server+Agent 분산 트랜잭션은 아닙니다.

## 5단계 — 정책·실제 애플리케이션 테스트

**Server REPL:**

~~~text
test internet-access source office-admin destination github service https
system audit
~~~

실제 허용된 출발지에서 [GitHub 접속 실습](/ko/use-cases/github-egress)을 사용해 Git 또는 curl 요청이 프록시를 통과하는지 확인하고 다른 FQDN은 DENY인지 검증합니다. **정책 ALLOW만으로 E2E 성공을 선언하지 않습니다.**

## 문제 해결·롤백

검증 실패는 변경 적용이 아니므로 오류 원인을 확인하고 다시 Diff합니다. **system diff <REVISION_A> <REVISION_B>**로 이력을 비교할 수 있습니다. **system rollback <REVISION>**는 현재 운영 접근 정책까지 바꿀 수 있으므로 승인받은 복구 상황에서만 실행하세요. 안전한 보관 기준에 따라 임시 YAML과 Export 파일을 정리합니다.
