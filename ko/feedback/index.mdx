## 제출하기 전에

1. 같은 문제나 요청이 있는지 [기존 GitHub Issues](https://github.com/datarelay-labs/datarelay-link/issues)를 먼저 검색하세요.
2. 추정한 최신 버전이 아니라 실제 설치되어 있는 DataRelay Link 버전을 적어 주세요.
3. 버그는 가능한 한 가장 짧고 안정적으로 재현되는 절차를 작성해 주세요.
4. 문제 파악에 필요한 범위의 로그와 진단 정보만 첨부하세요.
5. 공개 제출 전에 비밀정보와 고객 데이터를 반드시 제거하세요.

<Warning>
  **비밀번호, 개인키, enrollment token, API key, 고객 데이터 및 기타 비밀정보를 공개 Issue에 올리지 마세요.** 보안 취약점일 가능성이 있다면 공개 버그 양식을 사용하지 말고 먼저 유지관리자에게 비공개로 연락하세요.
</Warning>

## 좋은 버그 리포트에 포함할 내용

일반적으로 다음 정보가 있으면 문제를 훨씬 빠르게 확인할 수 있습니다.

- DataRelay Link 버전
- 문제가 발생한 기능 또는 구성요소
- 필요한 경우 Server OS와 Client OS
- 필요한 경우 배포 모드와 NAT/방화벽 환경
- 관련 CLIENT ID 또는 서비스 정보 — **비밀정보는 제외**
- 기대한 동작
- 실제 발생한 동작
- 정확한 재현 절차
- 필요한 범위로 정리한 `drlink` 진단 결과, 서비스 상태 또는 로그

간헐적인 문제라면 발생 빈도와 함께 reconnect, reboot, upgrade, restore 등 어떤 lifecycle 이벤트와 관련되어 있는지도 알려주세요.

## 좋은 기능 개선 요청 작성 방법

구현 방법만 적기보다 먼저 **해결하려는 문제**를 설명해 주세요.

예를 들어 단순히 "프로토콜 X를 추가해 주세요"라고 하기보다, 현재 어떤 작업을 수행할 수 없는지, 지금은 어떻게 우회하고 있는지, 어떤 플랫폼에 필요한지, 보안상 제약은 무엇인지, 실제 배포에 얼마나 중요한지 함께 설명하는 것이 좋습니다.

DataRelay Link는 의도적으로 **몇 대에서 몇십 대 규모의 소규모 환경**을 목표로 합니다. 따라서 대규모 fleet orchestration이나 전체 SASE/SWG 제품으로 범위를 확장하는 요청보다, 현재의 가볍고 이해하기 쉬운 운영 모델을 유지하는 개선 요청을 우선 평가하기 쉽습니다.

## 요청 가능한 영역 예시

- Secure Remote Access
- Controlled Egress
- enrollment 및 bootstrap UX
- 서비스 게시와 공개 포트 관리
- `drlink` CLI 및 운영자 UX
- lifecycle, upgrade, backup, restore, diagnostics
- Linux, macOS, Windows 호환성
- AI / MCP 통합
- 문서

<Tip>
  버그인지 기능 요청인지 애매하다면, 현재 동작과 기대한 동작을 설명한 뒤 주된 문제에 더 가까운 양식을 선택하세요.
</Tip>
