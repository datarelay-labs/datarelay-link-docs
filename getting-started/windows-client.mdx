# Windows Agent Host

Windows is an Agent Host platform; the DRLink Server remains Linux-based.

Use only the enrollment command generated by the Server.

## Enroll

On the Server:

```text
set enrollment zero-touch
```

In the wizard select **Windows → RDP only** or **Choose Remote Services**, enter the host name/description and actual target ports. Services selected through Zero-Touch **SSH only**, **RDP only** or **Choose Remote Services** automatically receive the required Service Object, Remote Service and public endpoint reservation during enrollment. Do not create the same service manually again. Inspect actual names with `show remote-services` on the Agent.

Run the generated Windows installation/enrollment command according to the product installation instructions.

## Verify

Open the DataRelay Link CLI on the Windows Agent Host and verify:

```text
show status
show agent
system info
system diagnostics
```

## Remote Services

Create only additional Remote Services on the Windows Agent Host after inspecting the enrollment-created services. RDP is represented as TCP/3389 through a Service Object; DataRelay Link does not enable RDP, create Windows credentials, or weaken Windows Firewall/NLA settings.

## Lifecycle

Use Agent lifecycle operations such as pause, resume, restart, product update, engine update, diagnostics, support bundle, and uninstall as exposed by the Windows CLI/package.

## Update an enrolled Agent

Upgrade the Server first. On the already enrolled Windows Agent Host, use elevated PowerShell:

```powershell
drlink system update product
drlink system version
drlink system diagnostics
```

Product update downloads the Server-qualified bootstrap over the existing pinned HTTPS management connection, verifies immutable provenance and SHA256, and preserves Agent identity, existing services and ports. Do not rerun Zero-Touch enrollment. If Source HEAD is UNKNOWN or mismatched, inspect the actual update result; do not edit provenance files. Relay Engine updates are separate (`drlink system update engine`).

## AI execution

Connected does not mean AI executor ready. The Windows lifecycle worker claims AI jobs only when an administrator explicitly opts into an existing protected local execution profile. AI Access remains the Server-side rule authority. The local account SID, allowed drive paths and command opt-in are independent OS execution constraints. Installation/update protects the product-owned executable/code tree from untrusted modification, without changing OS ancestor ACLs, enrollment or the existing profile. Diagnostics distinguishes an unsafe installed ACL from missing or invalid opt-in. An installed and authorized Windows Agent must be verified through actual tool calls. See [MCP tools](/reference/mcp-tools).
